Where the line sits today

What SPIL actually is right now

A two-part format: @keywords for structure, > directives for plain-English intent. The Planner writes it into a task. It's good — clean, ordered, readable by both human and model. But here's the catch ↓

🫥
Almost none of it is "run." Of every @section you write, the code only ever pulls out @success_criteria — and only at the very end, to hand Assurance (the grading agent) a checklist. Everything else is just text the model skims. Verified in server/src/services/SPILParser.ts — extractSuccessCriteria is the one function marked IN PRODUCTION.

Translation: SPIL today is a beautifully-organized sticky note. The structure helps the model think straight (that's the CTD ordering idea — foundations first). But the red lines are promises on paper. If the agent ignores @depends_on or skips the @context file, nothing stops it. Only the final grade is wired to code.
The path

Three stages: note → contract → language

It doesn't jump straight to "lisp." It crosses in two steps, and the value lands at stage 1 — long before it's a full language.

Stage 0 · today

The Note

model READS

Structured prompt. One field (@success_criteria) reaches code, at grading time. Helps the model; binds nothing.

→
Stage 1 · the bridge

The Contract

machine RUNS

Full parser → tree. Every @form becomes an instruction the orchestrator executes: deps become real schedule edges, criteria become a fail-closed gate, error conditions get checked.

→
Stage 2 · the language

The Language

program EVALUATES

S-expression core (code = data). Forms compose, macros generate tasks, the swarm is the runtime. An agentic orchestration language.

💡
The whole trick is one move: stop reading the @ parts and start executing them. That single shift — data the model interprets → instructions code enforces — is what turns a spec into a program. The lisp part (stage 2) is just what makes it composable after.
Why SPIL is uniquely able to do this

The split already baked in: @ vs >

SPIL's two symbols aren't decoration. They're already a clean line between "the deterministic part" and "the model part" — which is exactly the seam you need to grow a language without losing the LLM's flexibility.

@

becomes machine-executed

→ runs on ACT's deterministic layer (the orchestrator/server)
  • @depends_on → a real edge in the task graph. Scheduler won't start you until upstream is done.
  • @success_criteria → a runtime gate. Fails closed: no pass, no merge. Already half-wired (Assurance 95%).
  • @error_handling → guards the evaluator actually checks, not prose.
  • @context → auto-fetched into the window before the turn fires.
>

stays model-interpreted

→ stays the LLM's job (and that's the point)
  • > directives remain natural-language intent — taste, nuance, "do it this way."
  • This is the context-engineering layer: a language primitive that decides what text enters the window, when.
  • You keep the model's flexibility exactly where rigid code would be brittle.
  • Manifest + lazy-load (spil get) already point here — fetch the section, not the file.
🧩
This is the part most "agent DSLs" get wrong. They try to make the whole thing executable and lose the model's judgment, or keep it all prose and enforce nothing. SPIL already separates the two. You just teach the machine to run the @ half and keep letting the model read the > half.
Stage 2 · why lisp / scheme

The leap: when tasks can write tasks

Stage 1 makes SPIL run. Stage 2 makes it compose. Recast the @-forms as s-expressions and you get the lisp superpower: the program is data the program can edit. Now the Planner doesn't write 12 tasks by hand — it writes one macro that generates them.

stage 1 — runs, but staticCONTRACT
; one task, hand-written, executed
@task "Build auth login route"
@depends_on ["db-schema"]
@success_criteria:
  - returns ApiResponse<{token}>
  - tests pass

; ...and 6 more routes,
; copy-pasted by hand, each
; a separate CREATE_TASK.
Executable — but you still author every task by hand. The Planner is a typist.
stage 2 — composes itselfLANGUAGE
; one form generates the whole CRUD swarm
(for-each-route ["login" "logout" "refresh"]
  (task route
    (delegate backend_dev)
    (depends-on "db-schema")
    (criteria
      (returns "ApiResponse<{token}>")
      (tests-pass))
    > "follow existing middleware patterns"))

; criteria = a real gate. delegate = real
; routing. the > line still goes to the model.
Same primitives, now composable. criteria is the enforced gate from stage 1. delegate hits the real router. The > line still flows to the LLM. The macro wrote 3 enforced tasks from one line.
🌀
Why lisp specifically: a task graph is a tree, and s-expressions are trees written down. There's no gap to bridge — the syntax and the data structure are the same shape. That's "homoiconic" (code and data look identical), and it's the one feature that lets the orchestration language safely generate and rewrite its own plans.

The concrete answer: what part, and how

What changes, what stays

The crossing from "data framework" to "language" is one component: a parser that emits a tree + an evaluator that runs it, living in the deterministic layer (orchestrator.go / the server). The format barely changes. The handling of it does.

PieceTodayTo become a language
The syntax @keywords + > directives, free text Same symbols; add nesting + (optionally) s-expr form at stage 2 mostly KEEP
The parser SPILParser.ts — regex, extracts @success_criteria only Real tokenizer → AST (tree). Every @form becomes a node with meaning BUILD
The evaluator doesn't exist — nothing "runs" SPIL New: walks the tree, executes forms against ACT's existing orchestrator calls (delegate→router, depends_on→scheduler, criteria→Assurance gate) BUILD
@success_criteria Parsed at grading time; 95% gate exists Becomes the canonical fail-closed invariant the evaluator enforces pre-merge PROMOTE
> directives Text the model reads Stay exactly that — the model-interpreted context layer. Don't make these executable. KEEP
The runtime The swarm (Tier 2 agents) Same swarm — it's already your runtime. The evaluator just dispatches to it. KEEP
🛠️
Where it lives: the evaluator belongs in ACT's deterministic middle (orchestrator.go + server), per the Three-Layer rule — Planner decides, ACT executes state, Runner spawns. You're not adding a layer; you're filling in the one that already exists. The Planner already emits SPIL; today the server stores it as text — tomorrow the server evaluates it.
Keeping it honest

The one real risk — and why this version dodges it

The trap with custom languages: models write them badly because there's no training data. But that only bites when agents must write the user's project code in your language. This isn't that. SPIL-as-language is the orchestration layer — ACT's internal wiring for who-does-what, not the Python/TS the swarm ships. You own 100% of that corpus, the domain is narrow, and the user never has to read it. That's the safe wedge. Defaulting to a custom lisp for user deliverables on silence is still a bad idea — pick boring, safe Python there.
TL;DR — SPIL today: a sticky note the model reads, one field wired to code. To become an agentic language it needs one new thing — a parser-plus-evaluator that runs the @ forms while leaving the > forms for the model. That single move gives you all three buzzwords at once: orchestration (delegate/await as real ops), programmed invariance (criteria as a fail-closed gate), and a context-engineering language (directives + lazy-load as window control). The lisp/s-expr step comes last and only adds composability. Start at stage 1 — it's where the value is, and it's mostly promoting code you already have.
