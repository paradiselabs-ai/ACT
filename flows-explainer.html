F-no-authNo auth boundary on the server
The server mounts only cors(), express.static, and express.json. A grep for jwt|bearer|authorization|api[_-]?key|authenticate over index.ts returns nothing. Every endpoint is open on the bound port — anything that can reach it can create/complete/validate tasks, register agents, and read the full ChronLog. The trust boundary is localhost-only by accident, not by design.

F-qa-persistQA synthesis persists a marker, not the deliverable
POST /api/tasks/:id/synthesis (kind=complete) stamps metadata.synthesizedAt and logs a summary string to ChronLog. It does NOT persist the assembled final deliverable. The done-marker half works (and survives restart, which is why re-synthesis loops don't recur); the deliverable-storage half does not exist. Framing it as a full gap would be a bluff — the boundary marker is real — but framing it as "QA assembles and stores the deliverable" would be wrong.

F-95gate95% validation gate: prompt server-side, code-backstopped orchestrator-side
POST /api/tasks/:id/validation-verdict destructures and trusts the caller's passed/score verbatim — there is no server-side 95% check. The e2e fixture even posts passed:true score:95 with criteriaResults:[]. The real gate is two-part: the threshold instruction lives in the Assurance prompt, and the orchestrator's parseValidationVerdict adds a CODE backstop (passThreshold=95 plus FAIL-CLOSED on empty criteria, Fix 23). The server endpoint itself records whatever it is handed.

F-rebind-writefailBrief-accept Tier-1 rebind is skipped on AGENTS.md write failure
When a PROJECT_BRIEF is accepted, the orchestrator writes AGENTS.md and then rebinds all four Tier-1 system prompts so the project context reaches them mid-session. But the InvalidateContextCache + RebindSystemPrompt block lives inside the success (else) branch of the writeAgentsMd call. If the write fails, only a Warn logs — no rebind runs, and every Tier-1 agent keeps its startup prompt with NO project context for the rest of the session, silently.

F-rebind-busyRebindSystemPrompt busy-failure is unrecovered
RebindSystemPrompt returns an error when the agent is mid-turn / busy. The caller only Warn-logs that error and never retries. A Tier-1 role that happens to be busy at brief-accept time permanently misses its context rebind for that session. Idle-time rebind works; the busy/error case has no retry. This compounds F-rebind-writefail: two separate paths leave a Tier-1 agent context-blind with only a log line.

F-SHIMACP-backed Tier-1 shim CLI path is unbootstrapped by the installer (demotes a second-hand claim)
A slice inventory claimed the ACP Planner's prompt-section command was a dead path because cli/act-cli.ts has no prompt-section branch. Re-grep demoted that: prompt-section is handled natively in cmd/root.go:689 (pre-cobra, before any CLI routing), so both the in-process Planner (via the expand_prompt_section tool) AND the ACP shim reach it. The real, narrower gap is upstream: the shim execs exec.Command("act", ...) and relies on act-tier1-<role> symlinks on PATH, but install.sh creates ONLY an act-agent symlink, deliberately REMOVES any old act symlink (nektos/act collision), and never creates the act-tier1-<role> symlinks at all. After a standard install, ACP-backed Tier-1 agents can resolve neither the act binary name nor their role shims — the whole shim CLI surface is dead. The in-process Tier-1 path (native act_cli + expand_prompt_section) works fully.

How to read the diagram

Open architecture-flows.html next to this page. Three layers of meaning:

  • ok code-verified. The step's detail cites a file:line where the implementing code lives. Open that file at that line and you see the behavior the step describes.
  • prompt-only ⌕ behavior that lives in prompt text only. No compiler or middleware enforces it. The clearest examples: the greenfield 5-question intake, the brownfield 2-question + "Ready?" hard-stop, the Observer "@planner, make no decisions" instruction, and the five autoroute variant affordances — all are LLM-compliance, not code.
  • gap-found ⚠ documented but with no implementing code, or partially implemented. The findings above are the gap-found items; clicking the corresponding flow puts the gap arrows in red dashed lines.
Status unverified does not appear in the shipped diagram. It is a construction-time scratch marker — every instance had to be promoted to ok with a file:line cite, demoted to prompt-only, demoted to gap-found, or removed before shipping. The v7 verification script reports 0 bluffs and 0 unverified.
Why 36 flows (over the 15-22 band). This rebuild maps four subsystems the prior PVM-era diagram predated: the ACP Tier-1 backend (spawn / prime / turn / shim), the per-role tool subsets + section registry, the Tier-2 runner/CLI/provider stack, and the binary-bootstrap/install path. Each flow is a distinct, separately-verified choreography — collapsing them to hit 22 would hide the very handoffs the diagram exists to show. Flow narratives

Boot & routing

Binary bootstrap. act-agent routes pre-cobra: prompt-section and the CLI subcommands are handled before cobra parses; everything else falls to RunE (--agent headless, -p non-interactive, no-args TUI). The TUI path calls EnsureServerRunning, which PID- and health-guards a npx tsx server/src/index.ts auto-start.

Server replay. Startup restores all in-memory state (projects, tasks, agents, file locks) from the append-only ChronLog before opening the port; a dev_reset event voids prior events. PVM indexing starts after restore. A PID-file guard makes the process exit if a live duplicate is already running.

Intake & dispatch

Greenfield INTAKE. A 404 on the project lookup flips intakeMode on. The 5-question conversation lives entirely in the Planner's static prompt — the orchestrator only watches the output (a code comment confirms no per-turn injection). On PROJECT_BRIEF the orchestrator parses the brace-balanced JSON, POSTs CreateProject, clears intake, and fires BUILD via fireWhenPlannerIdle.

Brownfield INTAKE. Existing code + no server record triggers an off-startup onboard: a deterministic scaffold (codebase onboard --dir, 20s), then backend-aware researcher enrichment (claude-code subprocess or in-process, degrading to the scaffold), then a Planner 2-question intake. The analysis is folded into AGENTS.md as CodebaseNotes — unfenced (see F-agentsmd).

CREATE_TASK dispatch. The message-ownership loop dedups twice (once per msg.ID, once on a 60-second content hash), parses CREATE_TASK markers + a {tasks:[]} fallback, lazily spawns the swarm filtered by project.agents[] on the first batch, and creates tasks in two passes (create with empty deps + a title→ID map, then PATCH dependencies replacing sibling titles with IDs).

The four Tier-1 agents

Backend dispatch. Each Tier-1 role resolves its backend from ~/.act.json via a single switch in app.go: external hosts (claude-code; antigravity/agy in flight; codex/opencode accepted-but-unimplemented) drive over ACP; an empty backend keeps the in-process LLM path with a per-role tool subset and HistoryMode. The in-process Planner gets HistoryThread (its own notebook); Observer/Assurance/QA get HistoryNone (stateless snapshots).

Observer. A 120-second loop builds a parallel server snapshot, runs a seven-rule anomaly scan (including a three-way orphaned-pending classifier: wedged / unresponsive / unservable), and addresses @planner with suggested actions — the "make no decisions" instruction is prompt-only. A no-op signature gate suppresses repeats; a Tier-1 watchdog re-triggers stuck Assurance/QA before the Observer LLM fires.

Assurance. The validation poll loop routes one pending task at a time to Assurance with a per-criterion view/grep verification prompt. The verdict is parsed at passThreshold=95 with a fail-closed empty-criteria backstop (Fix 23): an empty-criteria 100% becomes a FAIL with re-emitted gaps. markSeen only on accept, so a parse/HTTP failure leaves the task retryable.

QA / Synthesizer. The QA loop routes one validated task at a time, builds a synthesis prompt from metadata.result + validationScore, and parses SYNTHESIS_COMPLETE / NEED_CLARIFICATION. metadata.synthesizedAt drains the queue (status stays validated); a NEED_CLARIFICATION addressed to a swarm agent routes to that agent's inbox and suppresses the Planner autoroute. Note F-qa-persist: the deliverable itself is never stored server-side.

Autoroute & visibility

Tier-1 → Planner autoroute. Non-Planner Tier-1 messages are forwarded into Planner turns with one of five variant-shaped prompts (Anomaly / PassVerdict / FailVerdict / SystemEscalation / SystemNoTask). The variant bodies are prompt-only affordances; the cap is code — a wall-clock sliding window (≤5 per 10 minutes, pruneAutoRoutes), cleared on every human input. The asymmetry matters: Planner replies don't autoroute.

Internal-prompt hiding. Injected (non-human) turns are prefixed with the InternalPromptMarker sentinel; the chat list skips marked user messages while the LLM still sees the full content. ACP priming rides the same marker because ACP has no system channel.

ACP Tier-1 backend (the layer the old diagram predated)

Turn lifecycle. ACPAgent spawns the host via buildCommand (claude-code → npx; antigravity/agy → node agy-acp.mjs, uncommitted), does the JSON-RPC initialize handshake, and primes the session ONCE with the role prompt as the first user message. runTurn sends content-only prompts (no transcript replay), stamps ThreadID=role on display messages, and streams agent_message_chunk deltas back.

Shim CLI. An ACP agent has no native act_cli tool, so it invokes its act-tier1-<role> shim over Bash; the shim re-enforces the same per-role allowlist and banned-metachar guard, then execs the real binary. prompt-section resolves natively in cmd/root.go. But the whole shim surface is unbootstrapped on a clean install (see F-SHIM).

Tier-2 swarm, CLI & providers

Swarm spawn. The orchestrator lazily spawns one Node runner per role on the first CREATE_TASK. Each gets an orphan sweep (pkill -f act-runner.mjs), its own process group (so the parent kills the whole subtree), an isolated ~/.act/runners/<role>.log, and a reaper goroutine.

Runner loop. Register (409 self-heals by DELETE+retry), claim a singleton (one in-flight task per agent id), inject the AGENTS.md brief, add complexity-triggered PVM context (score > 4), run the backend (claude-code vs act-agent — no antigravity branch, see F-agy-tier2), then complete → submit-for-validation. That submit chain is what feeds Assurance and QA; a failure skips validation.

Providers. NewProvider switches on ModelProvider: anthropic is native; the rest (openai/groq/openrouter/xai/local and the new NVIDIA NIM at integrate.api.nvidia.com/v1) route to the OpenAI-compatible client. A global response cache fronts the send path (catching Assurance re-scoring and Observer re-fires); streaming bypasses it. There is no model registry — the user writes the upstream model string verbatim in ~/.act.json.

What the diagram is for

Three purposes, in order of importance:

  • Honest map. A new contributor (or a future Claude session) opens the diagram and learns what the codebase actually does, not what the prose docs imply.
  • Gap surface. The fourteen findings are immediately visible. Next time someone proposes a feature depending on full QA deliverable persistence, a hot-swappable Tier-1 backend, or a Tier-2 antigravity runner, the gap is already documented — they know they have to close it first.
  • Self-discipline. Every ok step cites a file:line; sub-agent claims must be re-grep'd by the parent before being encoded. F-SHIM is this rebuild's proof: a slice inventory's "prompt-section is a dead path" claim survived only until the parent re-grepped cmd/root.go and found the native handler. The bluff was caught before it shipped.
