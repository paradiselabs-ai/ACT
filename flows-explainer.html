Findings (read this first)

Seven things the diagram surfaces that the prose-level docs either obscure or overstate. Each finding maps to a gap-found step in architecture-flows.html, or to prompt-only behavior that has no code enforcement. The taxonomy distinguishes code-enforced behavior from prompt-wished behavior — the binary ok/unverified in the prior diagram let sub-agents bluff, so it was replaced.

F-ANo auth boundary on server
CORS is open by default. Every endpoint on localhost:8080 is reachable unauthenticated. POST /api/dev/reset clears all in-memory state with no credentials. DELETE /api/agents/:agentId removes any agent by id. Socket.io accepts unauthenticated connections. The trust boundary is localhost only — if anything else can reach the port, the entire coordination state is open.

F-BSocket.io is vestigial
The server raises 27 io.emit broadcasts and registers 9 socket.on handlers. Neither the Go TUI nor the Node Runner imports a socket.io client — both use HTTP polling. So the broadcasts have no receiver and the handlers are dead listeners from the pre-CLI MCP era. Pulling these out would shrink the server surface area considerably, but the constraint here is no source-code edits inside the map work, so the diagram surfaces it rather than fixing it.
server/src/index.ts:1063-1280 · zero socket.io imports in act-agent/ or act-agent/runner/
F-Cact-coordination.json is human-written, not machine-written
The repo-root act-coordination.json is a manual log used to coordinate multiple Claude instances working on this codebase. No runtime code writes to it — a grep across server/src/ and act-agent/internal/ returns zero hits. The machine analogue is data/coordination-log.jsonl, owned by ChronologicalLog with a 5-second flush timer.

F-EQA synthesis persistence is partial
POST /api/tasks/:taskId/synthesis at server/src/index.ts:795 persists a synthesis_complete event and a short summary string to ChronLog. It does NOT persist the full synthesized deliverable text. The complete assembled artifact body lives only in the TUI session lifetime. So this is a partial gap — the event survives restart, but the deliverable does not. Framing it as a full gap (as the prior diagram did) would have been bluffing; framing it as fully implemented would be wrong too.

How to read the diagram

Open architecture-flows.html next to this page. The diagram has three layers of meaning:

  • ok code-verified. The step's detail cites a file:line where the implementing code lives. You can open that file at that line and see the behavior the step describes.
  • prompt-only ⌕ behavior that lives in prompt text only. No compiler or middleware enforces it. An agent could skip the behavior and the system would only catch it via another LLM judge. The clearest example is the Ralph Wiggum self-verification loop.
  • gap-found ⚠ documented but with no implementing code, or partially implemented. The seven findings above are the gap-found items. Clicking the corresponding flow on the diagram puts the gap arrows in red dashed lines.
Status unverified does not appear in the shipped diagram. It was a construction-time scratch marker — every instance had to be promoted to ok with a file:line cite, demoted to prompt-only, demoted to gap-found, or removed before shipping. The v6 verification script reports 0 bluffs and 0 unverified.

PVM rebuild chain (W01 → W10 + followup-a)

The PVM subsystem (PAIRed Vector Minutes — semantic memory of coordination events) was the focus of the last sprint. v5 of the map captured the chain through W09; v6 adds W10 and W10-followup-a. The chain is finished, the hardened wipe ran, the end-to-end test passes 22/22 against fresh data.

W01 — Mode gate

Real all-MiniLM-L6-v2 embeddings flipped on at LocalEmbeddingVectorStore. A mode field (:62) plus warmup race-safe announcement so the boot log says [PVM] real embeddings active exactly once. getMode() getter at :93 for runtime queries.

W02 — Per-event project tagging

extractProjectName at PVMIndexer.ts:36 reads data.task.metadata.projectName, data.metadata.projectName, data.projectName, or — only for project_created events — data.name. Anything else falls through to __global__. Tagging applied at both ingest sites.

W03 — Scoped search

Vector store, indexer wrapper, REST endpoint, runner injection, and CLI all thread a projectName through. Endpoint default stays cross-project; CLI default is scoped. __global__ events surface in every scoped query so harness-level wisdom isn't hidden behind project walls.

W04 — Backfill

POST /api/pvm/reindex at server/src/index.ts:1040 calls the idempotent indexAllEvents. act-agent pvm reindex CLI subcommand wraps the endpoint.

W05 — Xenova model install

Model dropped under node_modules/@xenova/transformers/.cache/Xenova/all-MiniLM-L6-v2/. Confirmed by the boot banner reporting dim=384. The Xenova cache survived the W10 wipe because it sits inside node_modules, which is outside the wipe whitelist.

W06 — Real analytics derivations

getAgentProfile (line 273), getAgentSynergy (line 366), compareAgents (line 428) re-implemented to derive from real task lifecycle JOINs via the new private lookupTaskOutcomes helper (line 475). Math.random placeholders and hardcoded 0.85 / 3600 / 0.95 constants all removed.

W07 — SelfImprovementEngine real derivations

Four stub methods (analyzeToolUsagePatterns at :404, analyzeCollaborationPatterns at :483, analyzeKnowledgePatterns at :565, calculateImprovementMetrics at :662) replaced with derivations from ChronLog event counts, taskId-join shared work counting, peer_response keyword-frequency topic extraction, and validated/completed ratio. analyzeCoordinationPatterns still placeholder by design — out of W07 scope.

W08 — ChronLog per-project split

ChronologicalLog dual-writes: the global JSONL plus a per-project mirror under server/data/projects/<projectName>/coordination-log.jsonl. Routing by extractProjectName; sanitization at projectLogPath (:247). Read paths getRecent and query accept an optional projectName argument. A one-shot migration script at server/scripts/chronlog-split.ts handled the v4-era backlog.

W09 — Follow-up fixes

Three things: (1) extractProjectName narrowed its data.name fallback to project_created events only — earlier behavior over-matched agent_registered.data.name and created bogus role-named buckets (Developer, Backend_Dev, etc.) under data/projects/. (2) Indexer added a typedTaskIds dedup set so the coordination-flavored duplicate of a typed lifecycle event is dropped in-batch — the richer typed event survives. (3) Analytics REST endpoints landed at :1062 (profile), :1077 (synergy), :1092 (compare).

W10 — Cursor regression + agent attribution

Two bugs. Bug I (cursor regression): POST /api/pvm/reindex made the cursor jump backwards to 2026-04-17 because ChronologicalLog.query() defaulted to limit=100; indexAllEvents was getting the OLDEST 100 events. Fixed at three layers — explicit limit:100000 in the indexer's two query calls (:145, :234), defensive default-no-limit in the query method itself (ChronologicalLog.ts:338), and a max-timestamp no-regression guard around the cursor write (:294-302). Bug J (agent field mismatch): the indexer was reading event.agentId, but ChronLog events carry event.agent at top level — so every indexed point got attributed to "system". Fixed at :191 and :268 with event.agent || event.agentId || 'system'. The whole work was then validated against the live data before any wipe.

W10 — Hardened wipe

Eight pre-existing storage targets were scheduled for deletion: data/coordination-log.jsonl, .pre-split.bak, the entire data/projects/ subtree, plus ~/.act/{act.db, act.db-shm, act.db-wal, agent-id, sessions/}. Per user constraint, the wipe was rewritten path-by-path with a wipe_assert_safe() helper that refuses symlinks, requires realpath under $ACT_ROOT/server/data/ or $HOME/.act/, and uses rm -- separator. Seven protected paths were asserted preserved after the wipe (~/.act.json, runners/, commands/, config.json, repl-config.json, server.log, the Xenova model cache). Final assertion: git status shows only the expected tracked-source diff, no wipe-target leakage into the working tree.

W10-followup-a — Schema mismatch fix

The post-wipe smoke surfaced a soft anomaly: every agent profile reported completedTasks: 0 despite real task lifecycle data. Root cause: the indexer's .map(event) was constructing the indexed CoordinationMessage from { timestamp, agent, message, type, scope, projectName } and dropping event.data entirely. lookupTaskOutcomes then walked this.points looking for m.data.taskId — which was always undefined — and silently skipped every event. The JOIN never fired. One-line fix at both .map blocks (PVMIndexer.ts:195-201 and :277-285): preserve event.data on the indexed point. Verified by synthesizing a minimal task_assigned + task_completed + task_validated triad and asserting completedTasks=1, successRate=1, reliability=1, avgTaskTime=60s.

Flow narratives (non-PVM)

The interactive diagram has 30 flows total; the PVM ones are covered in the chain section above. The summaries below mirror the prose attached to each non-PVM flow record in architecture-flows.json so you can read the narrative without clicking through.

Boot

TUI boot — User runs act-agent. cmd/root.go ensures the server is up, then app.New() creates four Tier 1 agents (Planner, Observer, Assurance, QA/Synthesizer) and five orchestrator goroutines.

Server boot — Server replays ChronLog into in-memory state (projects, tasks, agents, file locks) before opening the port. PVM indexing starts after restore.

Intake and task creation

INTAKE — Planner detects a new project (404), runs a 5-question conversation, emits PROJECT_BRIEF: {json}, orchestrator POSTs to /api/projects. The question sequence is enforced by prompt text only, so the agent could in principle skip a question and still emit a brief.

BUILD — Planner emits CREATE_TASK — Planner responses contain CREATE_TASK: lines. The messageOwnershipLoop parses them, orchestrator POSTs to /api/tasks. The first batch of tasks triggers the lazy swarm spawn.

Planner BUILD iteration — After INTAKE, every coordination event arriving through the 3 s poll loop turns into a new Planner turn — successes invite the next CREATE_TASK, failures invite retry, anomalies invite intervention. The branching logic between those three lives in prompt text, not in a coded state machine.

Capability-based routing — When Planner emits a task without pre-assignment, TaskCoordinator.assignOptimalAgent picks the best available agent whose capability set covers the task's requiredCapabilities. PVM-suggested agent considered first, then any matching available agent.

A2A external task push — External clients discover ACT via /.well-known/agent.json, then push tasks directly to a specific agent by id via POST /api/agents/:agentId/tasks. Pre-assigned, skipping the capability-routing step.

Per-Tier-1-agent dynamics

Observer's 6 anomaly categories — Observer monitors six categories of issues: stuck_task, stale_lock, idle_agent, unvalidated, bottleneck, file_conflict. Each has a documented detection rule in observer.go. Detection itself is LLM-driven against a status snapshot — not a coded rule engine. That is why every detection step shows up as prompt-only: the rules exist, but nothing enforces that the LLM applies them faithfully.

Assurance two-layer validation — Layer 1 verifies the agent's Ralph self-verification trace was present (prompt-only check). Layer 2 independently scores each @success_criteria item via view/grep against the project working directory (code-enforced — the tools are real). Score < 95 sends the task back to the agent; ≥ 95 forwards to QA.

QA need_clarification path — When QA can't assemble a coherent deliverable, it can request clarification from a specific agent. The synthesis endpoint accepts kind='need_clarification' with a targetAgent + question — recorded in ChronLog so the Planner sees it and decides where the question goes.

Per-Tier-2-swarm dynamics

Tier 2 role + backend selection — Each swarm role (developer / frontend_dev / backend_dev / qa_engineer / researcher) has its own prompt file and capability tags. Each role also has a backend choice: act-agent (the default, the Go binary) or claude-code (claude --print --dangerously-skip-permissions). Configured per role via /swarm <role> <backend>.

Swarm task context assembly — Before running a task, the runner pulls the agent brief and (for complex tasks only — score > 4) PVM patterns, parallel-agent awareness, and any pending inbox messages. buildTaskPrompt assembles these into a single prompt sent to act-agent or claude-code.

Runner polls and executes a task — Each runner subprocess registers, polls /api/tasks/assigned every 5 s, runs the chosen backend, and reports complete. The Ralph Wiggum self-verify step lives entirely in prompt text — no code gate at task complete time.

Recovery and rework

Task failure → retry or reassign — When a Tier 2 task fails (runner reports success=false, or Assurance returns task_validation_failed), Planner sees the event and decides: POST /api/tasks/:id/retry (same agent), emit CREATE_TASK to a different role, or escalate to the human.

Validation pipeline — Runner submits for validation. Orchestrator's validation poll loop picks the task up. Assurance scores against the working directory.

QA / Synthesizer assembly — Once Assurance passes, the qaPollLoop picks the task up. QA writes a synthesis_complete event with a short summary via the synthesis endpoint. The full deliverable text is NOT persisted server-side (finding F-E).

Coordination plumbing

Agent-to-agent messaging — Agents send direct messages to each other (parallel-coordination broadcasts, validation gap notes, clarifications). Server stores messages per-recipient via POST /api/messages; agents read them on context fetch via GET /api/agents/:id/messages. EventHub classifies them on the way in.

File lock claim — Swarm agents claim files before editing via POST /api/files/claim. Lock identity is a string compare of agentId. Conflicts return 409.

InternalPromptMarker auto-route — Observer, Assurance, and QA messages are prepended with \x00ACT_INTERNAL\x00 so the TUI hides the prompt but still shows the response with a role banner. autoRoutePlanner then triggers a Planner turn; a recursion guard caps the chain at 5 consecutive auto-turns, reset on every human input.

Per-turn 5-minute timeout — Every agent turn is wrapped in context.WithTimeout(ctx, 5 * time.Minute). On expiry the agent is canceled and a system message tells the user.

Background loops and event surfacing

Observer monitoring loop — Observer ticks every 120 seconds. When no anomalies are found it stays silent.

Coordination event surfacing — The orchestrator polls /api/log every 3 seconds and renders coordination events as system messages in the TUI chat.

ChronLog write and flush — Handlers append events synchronously to an in-memory buffer; a 5-second flush timer batches them out to data/coordination-log.jsonl. After each global flush, flushToJSONL groups the just-flushed buffer by extractProjectName and mirrors it into the per-project files (W08).

PVM indexing — Every 10 seconds, PVMIndexer fetches new ChronLog events and embeds them via LocalEmbeddingVectorStore (real all-MiniLM-L6-v2 embeddings). The in-memory vector store is ephemeral — recomputed every server restart. What changed since the prior explainer: the analytics layer on top of these embeddings is no longer placeholder data. getAgentProfile, getAgentSynergy, and (partially) compareAgents all derive from real task lifecycle JOINs through the W06 + W09 + W10-followup-a chain. The one residual filter bug in compareAgents is finding F-G above. Embeddings real, analytics now substantially real with one known-bad filter to chase.

Process group management

Spawn + orphan management — Each runner is its own process group (Unix only — Setpgid). On startup, SweepOrphans runs pkill -f act-runner.mjs defensively to clear leftovers from a crashed parent. The liveProcesses Map in act-runner.mjs enforces no-clone per agent id.

What the diagram is for

Three purposes, in order of importance:

  • Honest map. A new contributor (or a future Claude session) can open the diagram and learn what the codebase actually does, not what the prose docs imply.
  • Gap surface. The seven findings above are immediately visible. The next time someone proposes a feature that depends on, say, full QA deliverable persistence or compareAgents reporting real numbers, the gap is already documented — they will know they have to close it first.
  • Self-discipline. The constraint that every ok step cites a file:line is what makes the diagram honest. Sub-agent claims must be re-grep'd by the parent before being encoded into the JSON. This is the rule the prior session learned the hard way when a sub-agent claimed "QA persistence = full gap" using bad grep terms; the user caught the bluff because the actual endpoint at server/src/index.ts:795 was named synthesis.
